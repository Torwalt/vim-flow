# Planning AI work in Bend

*Working findings, 2026-10-26.* This project investigates whether laws and proofs
improve AI-produced code quality, reduce tokens spent exploring erroneous
approaches, or do both. Count the full workflow, including planning, witnesses,
proofs, failed probes, stronger-model help, review and repairs. Fewer implementation
retries or a low cached-token bill alone do not establish token savings.

## What the navigation run established

The first frozen handoff used erased equality premises that the pinned checker
would not accept in the attempted proofs. A stronger-model investigation and
repair were necessary. With ordinary premises and documented equivalent
contract revisions allowed, DeepSeek Flash completed seven units in one Ploopy
attempt each: 1h14m session time and $0.69 reported implementation cost. All
50 semantic obligations, plus 13 executable/type declarations, were filled in
the final checked graph. The original abstract Field/State boundary was usable.

The executor still spent 28m32s on find ranking, built substantial arithmetic
and scan-proof infrastructure, and revised line, find and digit predicates for
proof ergonomics. Review found missing browser blur handling, slow high-count
word movement and insufficient committed arbitrary-field runtime tests. A
kernel verdict covers stated core properties; browser wiring, specifications
and latency need independent evaluation. The [full review](../experiments/navigation-review.md)
records evidence, source landmarks, reproduction scripts and limitations.

This demonstrates feasibility of the revised workflow. There is no matched
TypeScript result yet, so neither better overall quality nor lower total tokens
has been established. The restart was assisted and is not an unchanged retry.

## Working planning rules

- The planner specifies public observations, supported inputs, validity,
  construction of arbitrary scenes, exact edge behavior and independently
  worked examples. Leave private storage and movement algorithms to execution
  unless a concrete feasibility problem needs more guidance.
- Validate a small real implementation witness with the pinned compiler before
  handing off proof signatures. Exercise ordinary/reusable/erased premises,
  abstract type filling and the runtime proof-assembly path. Merely elaborating
  open declarations is insufficient. Count witness code as planner assistance.
- Freeze behavior and supported domain rather than every proof-interface byte.
  Permit evidence-backed quantity/signature adjustments, equivalent predicates
  and shared helpers. Require old/new formulations, an obligation mapping,
  preservation evidence and independent examples, manifest updates and the full
  kernel verdict. Integrity hashes and unchanged declaration counts do not prove
  semantic preservation. Use equivalence proofs where practical.
- Share checked classification, normalization and arithmetic infrastructure.
  Index reusable lemma signatures/imports and factor proof modules by subject.
  A single growing proof file increases session reading and navigation cost.
  Avoid defining expected examples by calling production helpers.
- Keep the successful cumulative sequence: model, individual motion families,
  parser, browser. A unit must leave earlier obligations active and checks green.
  Give difficult rank/scan units a useful invariant description; split a green
  infrastructure unit when repeated evidence justifies it, not by default.
- Require tests through actual runtime constructors on varied fields, plus real
  browser input/focus behavior and high-count timing. Proved termination is not
  usable latency. Label newly introduced evaluation criteria separately from
  the historical handoff.
- Record failed approaches by cause: invalid contract interface, missing lemma,
  normalization resource limit, wrong runtime behavior or tooling/provider issue.
  Stop repeating an unchanged probe when it produces no new evidence. Preserve
  session statistics when available; one Ploopy attempt can contain many failures.

These are local findings from one feature, not a universal skill or a promise
about editing, dynamic worlds, Unicode or time. Existing lemmas should help
incremental work within this grid, but measure that benefit on the next feature.

## Comparing quality and token cost

The TypeScript arm is [Torwalt/vim-flow-ts](https://github.com/Torwalt/vim-flow-ts),
an independent snapshot of pre-implementation `main` at `0e17f02`, with the
ordinary Bun toolchain and comparable original contract assistance. Its plan
uses the same seven feature units and DeepSeek configuration; setup does not
start it. Full setup and migration work belongs in the accounting.

Compare both against independent shared behavior checks, then record defects,
repair work, latency and the next feature's cost. Keep tokens read/written and
cached/uncached separate; distinguish time and price from token quantities.
Count broader finite test coverage and universal proof coverage separately.
Explicitly disclose hindsight, provider/build changes and unequal planner help.
For stronger evidence, freeze a language-neutral next-feature brief and shared
acceptance criteria before preparing either language's plan.
